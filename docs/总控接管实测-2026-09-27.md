# 总控接管实测与实施约束

## 结论

本机已验证“自动化执行、主代理介入、恢复执行、独立核验回执”。Playwright 和 agent-browser 的页面操作故障均能由原生 Computer Use 接管；额外验证了 Playwright 执行进程被强制结束后，独立浏览器宿主保留页面，主代理介入后新执行进程连回同一页面。

主选保持 **Node 24 / TypeScript + Playwright 1.63.0 + 专用有头 Chromium + 独立 Browser Host**。agent-browser 0.38.1 保留辅助候选。接管通道已实测，生产队列、持久所有权、异常分流和 Neon/R2 验收仍待实施；本轮真实外链投稿新增 **0**。

## 本次实际做了什么

全部使用全新无凭据 profile 和自有 `127.0.0.1` 合成表单。浏览器保持可见，主代理用原生 `cua.getApp → setValue → getAXState → getScreenshot` 操作已确认的测试窗口，修改 Description；主代理不点击提交，交回执行器后才提交。

## 证据边界

- 前两项原始报告的 `samePage: true` 和 `takeoverMethod` 是人工观察/记录元数据，不是页面身份的自动证明；依据包括本会话原生 CUA 调用、截图、恢复后的字段与回执。第三项额外比较了实际 target ID。
- 当前验证了页面定位错误，以及浏览器宿主存活时的执行进程退出。没有验证浏览器宿主崩溃、网络分区、提交请求正在发送时中断、无人介入自动恢复。
- 此次独立 Chrome for Testing 的原生控制成功，不代表此前 Ego 的 ScreenCaptureKit `-3811` 已修复，更不意味着未来权限和系统捕捉永远不会失败。
- 没有访问扩展内部页、重载扩展、变更系统权限或操作日常 Ego/Chrome 标签。独立浏览器连接不是重做此前被拒绝操作的替代入口。
- Playwright 官方支持 [connectOverCDP](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)，同时明确其能力保真度低于原生 Playwright 协议。本次重连仅证明所测表单、附件和回执流程；复杂站点能力仍按适配器验收。

## 确定的分工与部署结构

```text
总控（主代理） ── 查看现场 / 暂停 / 接管 / 恢复 / 验收
       │                           │
       │ 任务 API                 └─ 原生 Computer Use → 原测试窗口
       ▼
持久任务队列（pg-boss + Neon，待实施）
       │
       ▼
执行 Worker（Node 24 / TypeScript / Playwright）
       │ 受控连接
       ▼
独立 Browser Host → 专用有头 Chromium / 隔离 profile
       │
       └─ 内容快照、动作记录、页面证据 → 现有 Worker API / Neon / R2
```

第一版部署在当前 macOS 的常驻进程中，保留已验证的本机原生接管条件。浏览器宿主负责启动、保活、实例身份和关闭；执行 Worker 负责逐站动作。两者生命周期分离，worker 崩溃不会主动销毁待接管页面。若以后搬到无桌面的服务器，需要另验可视化接管，不能沿用本次 macOS 结果。

主代理负责看现场、判断错误、修正规则或表单、授权恢复，并核验站方回执与精确的 Neon `destinationKey::profileId` 记录。持续跑批由常驻队列与执行器承担，不能依赖聊天回合一直保持活动。

生产实现必须满足：

1. **单一写入者。** 暂停请求必须等执行器确认动作结束、无在途提交后，才能转交主代理。旧执行器恢复后没有旧所有权的写入资格。
2. **持久所有权。** 记录 `jobId / attemptId / ownerVersion / browserInstanceId / targetId`，租约更新用数据库原子比较；恢复命令绑定本轮身份且只能消费一次。
3. **先核验再重试。** 可能已经提交的任务转入 `verify_pending`；站方证据未明确前不得自动重复发送。队列去重不能保证第三方站点端的恰好一次提交。
4. **异常只停单站。** 验证码、登录、付费、内容限制、浏览器控制失败分开登记；保存现场和最后动作后继续其他目标。需要用户输入的才交接用户。
5. **可检查的流水账。** 每项显示目标站、产品、实际提交内容与哈希、开始/提交/核验时间、当前步骤、阻碍类别、接管动作、回执 URL/截图与云端回读结果。
6. **不默认所有通道可用。** 原生 CUA 也失败时保留该任务，不把工具错误写成站点不可投稿，更不把重启或点击当作完成。

## 下一阶段的放行条件

本次完成的是接管可行性。生产改造先做隔离任务库的一条纵向流程：租约暂停/接管/恢复、执行进程退出、防重复提交、R2 证据、Neon 精确回读；再运行混合站点小批验收，最后扩到全库。已有 [浏览器选型](浏览器连接实测与选型-2026-09-27.md)、[架构审计](批量外链执行架构审计与改造建议-2026-09-27.md) 的全库标准仍适用。

诊断脚本见 [复现说明](../experiments/browser-selection/README.md)。静态恢复文件只用于单次诊断，不能直接作为生产总控接口。

审查：独立子代理只读复核了三项脚本与回执证据，主代理复核原生操作及服务器字段/附件哈希。归档脚本与现场执行文件一致，3 个文件语法检查及 `git diff --check` 通过；未变更生产执行代码，因此没有重复运行扩展全量测试。
